# Engineering foundations

Gravity adapts selected practices. It does not claim a full evaluation or standards compliance.

| Source | Practice |
| --- | --- |
| [QAW, third edition, §§3.5–3.8](https://www.sei.cmu.edu/documents/716/2003_005_001_14249.pdf) | Driver coverage, stakeholder priorities, six-part scenarios. |
| [ATAM, §7.2](https://www.sei.cmu.edu/documents/629/2000_005_001_13706.pdf) | Sensitivity points, trade-off points, and risks. |
| [TOGAF principles: worked example](https://www.opengroup.org/soa/source-book/togaf/p4.htm) | Statement, rationale, implications. Use the structure, not the example's service-oriented design. |
| [Attribute-Driven Design](https://www.sei.cmu.edu/library/attribute-driven-design-method-collection/) | Architectural drivers and externally imposed constraints. |
| [Domain model validation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-model-layer-validations) | Invariants across state changes. |

A **sensitivity point** strongly affects a quality outcome. A **trade-off point** affects multiple qualities, possibly in competing ways. For example, retry policy affects recovery, load, and duplicate effects.

For broader study: Bass, Clements, and Kazman, [*Software Architecture in Practice*, fourth edition (2021)](https://www.sei.cmu.edu/library/software-architecture-in-practice-fourth-edition/).

The combined document is Gravity's convention. Full workshops, voting, utility trees, and enterprise governance are optional. Read sources only to answer a relevant question.
